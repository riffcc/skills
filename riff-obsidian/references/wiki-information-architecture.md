# Information Architecture Style

## Goal

Keep the vault easy to navigate while letting content have whatever depth it deserves. Some topics need dense technical explanation, and others should remain lightweight checklists or quick reference pages. The architecture goal is not to force every note into one template, it is to keep people from getting trapped by fragmentation and memory loss.

## Navigation Model

There is no single mandatory start page. People begin from Obsidian search, the recent files list, graph view, or direct links from related notes. Domain indexes still exist where useful, but they are optional paths, not gates. If a person can find what they need in under thirty seconds from their own context, the structure is serving its purpose.

## Map and Context Design

Use folder structure as orientation, not law. The same project or decision should surface in at least two contexts: a product area and its execution record. This is how people discover it without knowing exact paths. Every major area should keep a small map, dashboard, or canvas so that new people can see “what lives where” at a glance.

## Metadata Model

Use stable properties across all notes where they exist: `type`, `status`, `owner`, `priority`, `created`, `due`, `project`, and `tags`. The property names stay the same everywhere so query views behave consistently. Use a property type consistently within the same meaning; if a property means “date” in one context, keep it a date in all contexts.

## Readability Standard

Write in prose with context, rationale, assumptions, and consequences. Keep language readable and specific. Long-form depth is expected for architecture, revenue, and cross-project dependency work. Short notes are fine for tactical updates and status calls. The standard is clarity first, then concision.

## Visual Standard

Every major domain should include at least one map, one status dashboard, and one evidence artifact such as screenshots, benchmark logs, or test traces. Visuals are not decoration. Every image, graph, or canvas should explain a decision, expose a risk, or record measurable progress.
